# 技术选型与实施路径

## 1. 技术原则

1. 微信小程序首发，但前端框架要保留 uni-app 能力。
2. 业务逻辑、接口层、状态管理、表单校验、上传能力尽量平台无关。
3. 所有微信专属能力都封装在适配层，避免在业务代码里直接散落调用。

## 2. 前端建议

1. 用户端小程序：采用 uni-app 开发，先编译到微信小程序。
2. 代办员端小程序：也采用 uni-app，和用户端共用基础能力层，但项目独立构建，避免角色权限和页面逻辑过度耦合。
3. 后台管理端：采用常规 Web 技术栈开发，负责运营、审核、结算和客服处理。

## 3. 为什么保留 uni-app

1. 后续可以低成本补 H5 落地页和运营页。
2. 若代办员后续需要更强定位、相机、离线能力，可扩 App。
3. 多端共用接口层、上传层、状态模型，整体维护成本更低。

## 4. uni-app 落地约束

1. 不要在业务代码里直接写微信平台专属对象调用。
2. 地图、支付、上传、订阅消息都做统一封装。
3. 样式和组件优先使用可跨端能力，减少后续迁移成本。
4. 涉及平台差异的地方用条件编译隔离。

## 5. 后端建议

1. 单体优先，模块化设计。
2. 核心模块包括：用户中心、服务中心、订单中心、报价中心、履约中心、内容中心、结算中心、消息中心、审核中心。
3. 存储建议：交易数据用 MySQL，缓存用 Redis，图片视频走对象存储。
4. 第三方能力：微信登录、微信支付、订阅消息、地图定位、短信、内容安全审核。

## 6. 风控与合规实现

1. 实名与资质审核：用户可选实名，代办员必须实名并审核。
2. 文件与凭证：上传时自动加时间水印、订单编号或节点说明。
3. 内容安全：纪念馆文案、留言、图片走内容审核链路。
4. 敏感服务：风水选墓等服务默认预约制，后台人工审核和人工派单。
5. 审计日志：派单、改价、退款、冻结等动作记录操作人和时间。

## 7. 分阶段实施路径

1. 第一阶段：做用户端小程序、代办员端小程序、后台管理端的最小闭环，只覆盖代祭扫、跑腿代办、咨询报价。
2. 第二阶段：增加纪念馆、云祭扫、消息提醒、评价体系、代办员评级。
3. 第三阶段：增加风水选墓预约、城市站点扩张、服务商合作、分账规则、营销系统。
4. 第四阶段：根据业务量决定是否扩 H5、App、企业微信协同工具。

## 8. 建议的开发顺序

1. 先定服务目录和订单状态机。
2. 再定三端页面和接口契约。
3. 再做后台派单与履约存证。
4. 最后补纪念馆与内容审核。
